\section{Mathematical definition of the problem}
Suppose that we have at our disposal a given graph $G = (V, E)$, where $G$ is the graph itself, $V$ denotes the set of all vertices (also called nodes), and $E$ represents the set of edges (also called links or arcs). An edge connects two nodes between them. The primary goal is to detect and count the number of triangles that can be formed inside the graph. More specifically, a \textbf{triangle} in graph $G = (V, E)$ is a set of three distinct vertices $\{u, v, w\} \subseteq V$ such that the edges $(u,v)$, $(v,w)$, and $(w,u)$ all exist in the set of edges $E$. This problem can be solved essentially using two distinct main approaches:
\subsection{Graph Traversal/Iterative Methods}
This category encompasses algorithms like the \textbf{Node Iterator} or the \textbf{Edge Iterator} that directly explore the graph, and at each iteration they try to look for the specific pattern that defines a triangle (three mutually connected vertices, as said before). They operate by iterating through parts of the graph (by scanning the list of either its nodes or edges) and checking for connections.
\subsection{Linear Algebra/Matrix Methods}
In this category, we mainly recall the \textbf{Matrix Multiplication} approach, which only works if the graph is represented by an adjacency matrix, which leverages matrix operations, specifically cubing (i.e. matrix multiplication) and trace computation, to get the exact number of triangles which can be created. Given the graph adjacency matrix $A$, this number is computed as $$\frac{1}{6} \text{ Trace}(A^3)$$ In graph terms, this trace represents the total count of all closed walks of length 3 in the graph, summed across all possible starting/ending vertices. 

\section{Node Iterator Algorithm, Forward Algorithm}
The simplest and most naive version of the Node Iterator Algorithm iterates over all nodes in the graph and, for each pair of neighbors of each node, checks whether they are connected by an edge. For each vertex, its \textbf{degree} $d(v)$ denotes its neighbors. If we have $V$ vertices, for each of them, we test unique pairs of neighbors that can be formed from $d(v)$ items. So, the overall complexity can be expressed as
\begin{align*}
\text{Complexity} &= \sum_{v \in V} \binom{d(v)}{2} \\
&= \sum_{v \in V} \frac{d(v)!}{2!(d(v)-2)!} \\
&= \sum_{v \in V} \frac{d(v) \cdot (d(v)-1) \cdot (d(v)-2)!}{2 \cdot 1 \cdot (d(v)-2)!} \\
&= \sum_{v \in V} \frac{d(v) \cdot (d(v)-1)}{2}
\end{align*}
In this project, we resorted to the so called \textbf{Forward Algorithm}, a variant which aims at improving complexity by iterating over vertices in a specific order, and efficiently queries their neighbors to identify potential triangle closures. We first implemented the \textbf{sequential} version of the algorithm, using \textbf{C++}, in which we can identify three main data structures used:
\begin{itemize}
    \item \textbf{Graph Representation:} How the graph's vertices and edges are stored, enabling efficient retrieval of a node's neighbors. We used and analyzed two primary representations: \textbf{adjacency matrices} (implemented as \texttt{std::vector<std::vector<int>>}) and \textbf{adjacency lists} (implemented as \texttt{std::map<int, std::vector<int>>} to handle potentially sparse or non-contiguous node IDs).
    \item \textbf{Auxiliary Sets (\textit{A[t]}):} Data structures used to store a specific subset of neighbors for each node (implemented as \texttt{std::vector<std::set<int>>}, where the outer vector is indexed by the node ID). These sets are then intersected (as defined in set theory) to identify the third vertex of a triangle.
    \item \textbf{Ordering/Ranks:} Structures (a sorted list of vertices and a map for ranks) to maintain and query the chosen ordering of vertices. Ranks are crucial for \textbf{pruning} and guarantee that each triangle is counted exactly once and that the search space is significantly reduced. Our implementation orders vertices by their degree (from highest to lowest) to optimize performance.
\end{itemize}
\subsection{Forward Algorithm V1}
In the file \texttt{seq\_node\_it\_v1.cpp} there's the implementation using the adjacency matrix. An entry \texttt{adjacencyMatrix[i][j]} is 1 if there is an edge between vertex \texttt{i} and vertex \texttt{j}, and 0 otherwise. So, with N nodes, the space complexity to store the matrix is $\mathcal{O}\left(N^2\right)$. Neighbor retrieval is linear, as it's mandatory to scan the full row of the node inside the matrix. The auxiliary set is defined as \texttt{std::vector<std::set<int>> A}. When processing an edge \texttt{(s, t)}, the algorithm needs to find common elements between \texttt{A[s]} and \texttt{A[t]}. As \texttt{std::set} stores elements in sorted order, \texttt{std::set\_intersection} can be efficiently applied, resulting in a complexity of $\mathcal{O}\left(K_0 + K_1\right)$, being $K_0$ and $K_1$ the sets sizes. For the orderings we use \texttt{std::map<int, int> ranks} and \texttt{std::vector<int> orderedList}.Checking rank condition takes $\mathcal{O}\left(\log N\right)$ for map lookups, and we iterate through the whole \texttt{orderedList} so it takes $\mathcal{O}\left( N\right)$. \\
\subsection{Forward Algorithm V2 (better version) and comparison}
In the file \texttt{seq\_node\_it\_v2.cpp} we used the adjacency list, coded as a \texttt{std::map<int, std::vector<int>>} to better handle potentially sparse or non-contiguous node IDs. This version is \textbf{more efficient}: to find the neighbors of a vertex u, the algorithm performs a lookup in the map ($\mathcal{O}\left(\log N\right)$) and then copies the associated vector of neighbors ($\mathcal{O}\left( d(u)\right)$). This is significantly more efficient for sparse graphs than iterating an entire row of an adjacency matrix. \\

\section{Parallel Forward Algorithm}
In order to achieve better performances, we created two concurrent versions of the Forward Algorithm which iterates through graph nodes. As we did with the sequential version, the first one uses the adjacency matrix to represent the graph, whereas the latter employs the adjacency list. 
\subsection{Parallel Forward Algorithm V1 and related flaws}
In the first version of the algorithm, more naive and simple case, the part that gets parallelized is the Forward algorithm function. More in detail, the outer loop that iterates through the nodes in the ordered list is still sequential, running $N$ times, but the \textbf{iteration over each node neighbors t is parallelized}: this is achieved by dividing the neighbors of s into chunks, with each chunk processed by a separate worker thread using \texttt{std::async}. Each worker thread is responsible for computing intersections and updating the auxiliary sets (\texttt{A[t]}) for its assigned subset of neighbors. To protect data races and guarantee mutual exclusion over the variable to count the number of triangles and the auxiliary sets, we resorted to \textbf{mutexes} (efficiently used with C++ \textbf{RAII lock templates}). However, this first version does not improve the execution time of the algorithm compared to the sequential version, and the asymptotic worst-case complexity is unlikely to improve substantially. The mutexes \textit{de-facto} serialize operations on shared data, meaning that even with P threads, the core set operations effectively run in a serialized fashion due to \textbf{contention}. Moreover, the additional overhead related to thread creation (which becomes higher and higher as the number of threads used increases) actually \textbf{slows down} the process even more. During our tests, we observed that the excessive overhead was harmful to the performances of the algorithm:
\includegraphics[width=0.52\textwidth, height=10cm, keepaspectratio]{charts/Parallel Node (Forward) V1 - Graph 10k Nodes - Intel Core i7 14th gen.png}
If we lower the number of vertices in the graph to, let's say, just 100, we can see that the parallel version of the algorithm becomes very inefficient, even counterproductive. This is because the time spent creating threads and managing context switching is presumably much higher than the computational gain achieved through parallel execution for such a small problem size. As a result, the overhead negates any potential speedup, making the sequential version the more performant choice:
\includegraphics[width=0.52\textwidth, height=10cm, keepaspectratio]{charts/Parallel Node (Forward) V1 - Graph 100 Nodes - Intel Core i7 14th gen.png}
\subsection{Parallel Forward Algorithm V2: improvements and scalability limitations}
We can now show a much better and efficient version of the Parallel Forward Algorithm. Indeed, this second parallel version achieves \textbf{true parallel speedup of the parallelizable portion of the algorithm}, which is the $\mathcal{O}\left(M \cdot d_{max}\right)$) part. This approach uses an adjacency list graph representation (\texttt{std::map<int, std::vector<int}) (which improves neighbor retrieval time from $\mathcal{O}\left(N\right)$ to $\mathcal{O}\left(\log N + d(v)\right)$ ) combined with a different parallelization strategy: instead of parallelizing the neighbors scanning for each single node inside each iteration of the algorithm, we now parallelize the outer loop of the Forward Algorithm. The ordered list of vertices is divided into contiguous chunks, and each thread is assigned a chunk of vertices to process independently. So, in other words, each thread performs the \textbf{full triangle enumeration logic for its assigned vertices in a totally independent way}, in parallel with other threads. Also, the The total count of triangles (variable \texttt{countTriangles}) is managed using \texttt{std::atomic<int>}, this significantly \textbf{reduces contention} compared to using mutexes for every triangle found. Another perk of this new version is that, since threads primarily operate on independent chunks of the ordered list of node, there is \textbf{minimal contention} on other shared data structures( \texttt{adjacencyVectors} and \texttt{ranks} ). Speaking more in depth about the theorical achievable speedup, given that the $\mathcal{O}(M \cdot d_{max})$ work (from the sequential version) is distributed among \textbf{P threads} with very low synchronization overhead (primarily from using atomic variables instead of mutexes), the ideal parallel time complexity can be written as:
\begin{align*}
\mathcal{O}\left(\frac{M \cdot d_{max}}{P} + (M + N \log N)\right)
\end{align*}
where $(M+NlogN)$ is related to the sequential pre-processing overhead. So, for sufficiently large $M \cdot d_{max}$, \textbf{we are able to achieve a significant speedup, proportional to P} (number of thread used), compared to the sequential version. This can be seen also in our experimental tests:
\includegraphics[width=0.52\textwidth, height=10cm, keepaspectratio]{charts/Parallel Node (Forward) V2 - Graph 10k Nodes - Intel Core i7 14th gen.png}
If we compare the two versions of the parallel algorithm, using this same graph, we can see that with every number of threads used we have a significant reduction of time, \textbf{approximately 3 orders of magnitude lower.}
In addition, using the adjacency list representation gives us the possibility to test much bigger graphs. Here are the results using graphs having 1 million of nodes:
\includegraphics[width=0.52\textwidth, height=10cm, keepaspectratio]{charts/Parallel Node (Forward) V2 - Graph 1 ML Nodes - Intel Core i7 14th gen.png}
However, if we use even \textbf{larger graphs}, we start to see the potential flaw of this second verision: \textbf{it doesn't yet reach full scalability}. As a matter of facts, this algorithm does not scale well because of two main defects:
\begin{itemize}
    \item Each thread performs the same, time-consuming operation of building the ranks map. This is \textbf{not a parallelizable part of the code} and severely limits the total speedup, as per \textbf{Amdhal's Law}.
    \item While an atomic variable is better than a mutex, constantly writing to the same memory location from multiple cores causes \textbf{contention} and introduces a significant amount of cache coherency overhead, which can degrade performance as the number of threads increases.
\end{itemize}
For example, with a graph of 100 million nodes, the algorithm achieves its maximum performance with 8 threads. Beyond this point, the performance begins to \textbf{degrade}. At 24 threads, the increased overhead is so severe that the program takes longer to complete than with only 2 threads, highlighting the detrimental effects of the sequential bottlenecks and excessive contention.

\subsection{Parallel Forward Algorithm V3: final version}
The final version of our algorithm is the \textbf{most efficient and scalable}. \\
\textbf{Amdahl's Law} states that the speedup of a program from parallelization is limited by the sequential fraction of the program. The new algorithm has a much smaller sequential fraction. The work is mostly done in parallel across the chunks, as the only sequential parts are the loop that launches the workers and the final loop that waits for them to complete. This allows the speedup to continue scaling as you add more threads. In this case, we resorted to \textbf{C++ tasks} (by means of \texttt{std::async}) instead of threads, to let the OS decide the appropriate time to efficiently schedule them, although we explicitly set the launch policy to \texttt{std::launch::async}. The most significant improvement is related to the \textbf{ranks creation} which is now executed just once, before launching all the tasks to avoid redundant and time consuming work. Moreover, we introduced a \textbf{thread-local count}, summed at the end, which eliminates atomic contention, leading to better scalability with more threads. The core of the algorithm was also re-designed from the ground up, introducing \textbf{unordered sets} to achieve much faster node or rank look-ups when using the adjacency lists or the rank sets (with this solution look-ups now take $\mathcal{O}(1)$ on average, instead of $\mathcal{O}(\log N)$). Using \texttt{std::unordered\_set} is also beneficial for \textbf{neighbor intersections}, which are now performed by means of \textbf{two-pointer scans on sorted lists} (in a \textit{merge-like} fashion), achieving a complexity of $\mathcal{O}(k_0 + k_1)$. Compared to the previous approach, this is dramatically faster and more memory-efficient, because it avoids repeated memory allocation.

\subsection{CUDA Parallel Forward Node Algorithm V1}
The inherent massive parallelism of the Forward Algorithm makes it exceptionally well-suited for execution on Graphics Processing Units (GPUs) using NVIDIA's CUDA platform. GPUs, with their thousands of arithmetic logic units (ALUs) and high memory bandwidth, can process a multitude of edges concurrently, offering a significant performance advantage over multi-threaded CPU implementations, especially for very large graphs.
To efficiently handle graph data on the GPU, the sparse adjacency list of the graph is converted to \textbf{Compressed Row Storage (CRS)} format on the host. This representation consists of two primary arrays: a row pointer array and a column index array, which are then transferred to the GPU's global memory using \texttt{cuda\_runtime} library functions. This dense storage format is well-suited for \textbf{coalesced} memory access. ON the host side, we initialize the ranking (in a similar way like we did with the V3 version of the C++ Parallel Forward Algorithm). As we already said, this ranking is essential for the parallel algorithm's correctness and efficiency, as it is used to enforce a strict ordering on the traversal of the graph. The core of the algorithm is performed inside the \texttt{ForwardAlgorithmKernel} \textbf{kernel function}, where we assign \textbf{each GPU thread to a graph node}. Within the function, the approach to identify a potential triangle formed by vertices $(s, t, v)$ remains the same as with the C++ versions. Then, To handle concurrent updates to the global triangle counter from multiple threads, the \texttt{atomicAdd} function is used. This ensures thread-safe accumulation of the total count.
The parallel strategy of the CUDA V1 Forward Algorithm is heavily dependent on the configuration of its launch parameters, particularly the \texttt{blockSize}, which serves as a critical \textbf{hyperparameter} for performance tuning. As a matter for facts, while the \texttt{gridSize} is mathematically derived to ensure all graph nodes are processed, the selection of Block Size involves a trade-off between several factors like warps occupancy or memory utilization. \\
When we set the \texttt{blockSize}, we are essentially telling the GPU how many threads to put into a single block. Since, in current architectures, a warp is composed of \textbf{32 threads}, using multiples of 32 can result in the block containing an exact number of full warps, so the GPU can schedule them more efficiently.
Here are the result using different configurations, tested on the 100 million nodes graph:
\includegraphics[width=0.52\textwidth, height=10cm, keepaspectratio]{charts/CUDA Node V1 - Graph 100ml Nodes - RTX 4060 Laptop GPU.png}
We can see that the best performance is achieved setting \texttt{blockSize} to 128, resulting in approximately 25 ms of execution time (this includes also the time spent copying data using from the Host to the Device using the PCIe buffer). Then, the execution time significantly worsens as the size of a block increases to 256, 512, and 1024. In facts, when \texttt{blockSize} is small to moderate (i.e. 64 or 128) the blocks are "lightweight" and many can be scheduled simultaneously on an \textit{SM}. This leads to \textbf{high occupancy}, which is crucial for hiding memory access latency. If, on the other hand, we set the size of each block to a much higher number (i.e. 512 or 1024), the resource requirements for a single block might be so high that the SM can only schedule one or two blocks at a time. This drastically reduces occupancy.

\subsection{CUDA Parallel Forward Node Algorithm V2}
In the second version of the algorithm, we used a \textbf{Merge-Like} approach to handle neighbors intersections and look to for the third vertex to complete each triangle. his method uses two pointers (p1 and p2) that traverse the respective neighbor lists, which are stored in the CRS columns \texttt{d\_adjacencyList\_colIdx} array. This approach has a time complexity proportional to the sum of the degrees of s and t, making it more efficient than a naive nested loop. 
While this merge-like intersection is a considerable improvement in algorithmic complexity, it introduces potential challenges related to \textbf{warp divergence}, a well-known issue in GPU programming. For maximum efficiency, all threads in a warp should execute the same instruction at the same time.

In our kernel, two key areas are susceptible to warp divergence:

\begin{enumerate}
    \item \textbf{Outer Loop Pruning:} The condition \texttt{if (rank\_s >= d\_ranks[t]) continue;} is a point of potential divergence. If some threads in a warp are assigned to nodes $s$ that satisfy this condition, while others are assigned to nodes that do not, the warp must execute both the \texttt{continue} path and the rest of the loop sequentially. This effectively reduces the parallelism of the warp from 32 threads to a smaller number, or even 1, for that instruction cycle.
    
    \item \textbf{Inner Intersection Logic:} The \texttt{if-else-if} block within the \texttt{while} loop is another critical source of divergence. Threads processing different pairs of neighbor lists $(s, t)$ will have varying \texttt{v1} and \texttt{v2} values. This means that within a single warp, some threads might take the \texttt{v1 == v2} path, while others take \texttt{v1 < v2} or \texttt{v1 > v2}. The GPU will then serialize the execution of these different paths, executing each branch separately, which diminishes the warp's throughput and performance.
\end{enumerate}

Overall, the second version of the algorithm is able to execute in less time compared to a simple nested loop due to its superior algorithmic complexity and the use of thread-level parallelism. However, the performance is still subject to the overhead of warp divergence caused by conditional branching. This overhead becomes more pronounced in graphs with a wide degree distribution, where the paths and lengths of the neighbor lists vary greatly among different threads within the same warp.

\section{Edge Iterator Algorithm}

The Edge Iterator Algorithm, often referred to as a variant of the Forward Algorithm for triangle counting, takes a different approach to traverse the graph compared to the node-centric iteration. It focuses directly on processing each edge in the graph to identify triangle closures.

A core principle shared with some optimized node iterator algorithms is the use of a specific vertex ordering (ranks), typically based on degree (from highest to lowest), to avoid redundant counting and optimize the search. This ordering creates a "forward" direction for edges and relationships.

In this algorithm, for each edge $(u, v)$ such that $rank(u) < rank(v)$, the algorithm seeks a third vertex $w$ that is a common neighbor of both $u$ and $v$, and also satisfies the condition $rank(w) > rank(v)$. If such a $w$ exists, then $(u, v, w)$ forms a triangle. Each triangle is counted exactly once due to this strict rank-based ordering.

To facilitate efficient and non-redundant iteration, the implementation introduces a dedicated \texttt{edgeSet}. This set stores all unique edges in the graph. In our C++ implementation, this is achieved using an \texttt{unordered\_set<Edge>} (where \texttt{Edge} is a custom struct with a specialized hash function to handle \texttt{(u,v)} and \texttt{(v,u)} as the same edge). While the \texttt{edgeSet} itself doesn't directly enforce the rank condition during its creation, the \texttt{EdgeIteratorAlgorithm} function applies the rank check (\texttt{if (ranks.at(v0) > ranks.at(v1)) \{ swap(v0, v1); \}} and \texttt{if (ranks.at(v) > ranks.at(v1))}) during its iteration to ensure that each triangle is counted exactly once according to the forward algorithm's principles. This allows a clean iteration over graph edges, decoupling the triangle counting logic from the underlying graph representation.

A crucial aspect of this algorithm's efficiency lies in how it finds common neighbors. For each edge $(u, v)$ being considered, the algorithm retrieves the \textit{full} adjacency lists (neighbors) of both $u$ and $v$. The intersection of these two adjacency lists (\texttt{neighborsV0} and \texttt{neighborsV1}) yields the set of common neighbors. Each node $w$ in this intersection forms a triangle with $u$ and $v$, provided the rank condition ($rank(w) > rank(v)$) is met.

Compared to the basic Node Iterator version, the Edge Iterator offers several advantages:

\begin{itemize}
    \item \textbf{Fewer iterations:} Instead of looping over all nodes and then all pairs of their neighbors, the algorithm directly processes each edge. This can significantly reduce the total number of primary iterations, especially in sparse graphs where $M$ (number of edges) is much smaller than $N^2$.
    \item \textbf{Direct Edge Processing:} The algorithm's focus on edges makes it naturally suited for sparse graphs, where the work done is proportional to the number of existing connections rather than potential connections.
    \item \textbf{Efficiency with Ordered Neighbors:} When adjacency lists are used and sorted (either explicitly or implicitly through data structures like \texttt{std::set} or by sorting \texttt{std::vector} neighbors), finding the intersection of neighbor lists can be very efficient, often linear in the size of the smaller list.
\end{itemize}

As with the Node Iterator, we implemented two versions of the Edge Iterator Algorithm, primarily differing in their underlying graph representation:

\begin{itemize}
    \item In \texttt{seq\_edge\_it\_v1.cpp}, the graph is stored as an adjacency matrix (\texttt{std::vector<std::vector<int>>}). Neighbor retrieval involves scanning a row of the matrix, which can be inefficient for sparse graphs. The space complexity is $\mathcal{O}(N^2)$.
    \item In \texttt{seq\_edge\_it\_v2.cpp}, an adjacency list is used, implemented as \texttt{std::map<int, std::vector<int>>}. This representation is generally more efficient for sparse graphs. Retrieving neighbors from a \texttt{std::map} takes $\mathcal{O}(\log N)$ for the map lookup plus $\mathcal{O}(d(u))$ to access the vector of neighbors. The intersection between neighbor lists (which are \texttt{std::vector<int>} here) is performed using \texttt{std::set\_intersection} after sorting, or by direct two-pointer intersection if the vectors are kept sorted.
\end{itemize}

Overall, the Edge Iterator Algorithm, especially when combined with an adjacency list representation and degree-based ordering, often provides a more efficient approach to triangle counting in terms of both time and space complexity, particularly for large and sparse graph datasets.

\section{Parallel Edge Iterator Algorithm}
The Parallel Edge Iterator Algorithm is a method to concurrently count triangles in a graph by distributing the workload among multiple threads. This approach is highly effective because the triangle enumeration for each edge is an independent task. We created two concurrent versions, each with a different underlying strategy for finding common neighbors between two vertices, and their performance, tested on an \textbf{Intel(R) Core(TM) i7-14650HX (2.20 GHz)}, reveals crucial insights into the trade-offs of parallelization and workload size.

In the first, more naive version (\textbf{Parallel Edge V1}), we parallelize the outer loop that iterates over each edge. We distribute the edges among threads, and each thread is responsible for processing its assigned chunk. For a given edge (s,t), the thread finds common neighbors by performing a \textbf{naive nested-loop intersection} on the neighbor lists of s and t. This method of finding common neighbors has a worst-case time complexity of O(d(s)${\cdot}$d(t)) per edge, where d(s) and d(t) are the degrees of the vertices. The total count of triangles is managed using an std::atomic<int>, which significantly \textbf{reduces contention} compared to using mutexes. However, as shown in our experimental tests, the effectiveness of this approach is highly dependent on the graph size. On a larger graph with 10k nodes, the computational workload is substantial enough that the parallel gains outweigh the thread management overhead, leading to a consistent decrease in execution time as the number of threads is increased. The performance flattens out around 8 threads, but importantly, it does not degrade significantly even with more threads, as the workload is not large enough to create substantial overhead.
\includegraphics[width=0.52\textwidth, height=10cm, keepaspectratio]{charts/Parallel Edge V1 - Graph 10k Nodes - Intel Core i7 14th gen.png}
This is not the case for a smaller graph, such as the one with 100 nodes. On this graph, the computation is so quick that the overhead of creating and managing multiple threads becomes a dominant factor. The graph below shows erratic performance with increasing threads, even degrading significantly at 8 threads, because the operating system is spending more time on context switching and thread scheduling than the threads are spending on actual work. For such small problems, a single-threaded sequential approach is often superior.
\includegraphics[width=0.52\textwidth, height=10cm, keepaspectratio]{charts/Parallel Edge V1 - Graph 100 Nodes - Intel Core i7 14th gen.png}

To achieve a more substantial and true speedup, we developed a second, much more efficient version (\textbf{Parallel Edge V2}). This version uses an adjacency list representation and employs a crucial preprocessing step to ensure all neighbor lists are sorted. With sorted lists, each thread can find the common neighbors for its assigned edges using a \textbf{two-pointer merge-like algorithm}, which has a linear time complexity of O(d(s)+d(t)). This significant improvement in the intersection process allows the algorithm to achieve a speedup proportional to the number of threads used, \textbf{P}, with very low synchronization overhead from the std::atomic variable. The ideal parallel time complexity can be written as:
\begin{align*}
\mathcal{O}\left(\frac{\sum_{(s,t) \in E} (d(s)+d(t))}{P} + (M \log N)\right)
\end{align*}
where MlogN is related to the sequential pre-processing overhead of sorting the neighbor lists. This approach yields significant performance improvements across all graph sizes.

Our analysis of the V2 algorithm on various graph sizes highlights its efficiency and how it scales differently based on workload. On a 10k-node graph, we observe a dramatic and consistent drop in execution time as the number of threads increases, with an optimal point around 8 threads. The performance is consistently better than the V1 version on the same graph, demonstrating that the linear-time intersection is far superior to the naive nested-loop approach.
\includegraphics[width=0.52\textwidth, height=10cm, keepaspectratio]{charts/Parallel Edge V2 - Graph 10k Nodes - Intel Core i7 14th gen.png}

The scaling benefits of the V2 algorithm become even more apparent on extremely large graphs. For a graph with 1 million nodes, the performance curve shows a near-linear decrease as the number of threads increases up to 8. This indicates a near-perfect parallel speedup where the workload is large enough that the benefits of parallelization far outweigh the overhead.
\includegraphics[width=0.52\textwidth, height=10cm, keepaspectratio]{charts/Parallel Edge V2 - Graph 1ml Nodes - Intel Core i7 14th gen.png}

This trend continues with an even larger graph of 10 million nodes, but with a more pronounced effect. The computation time decreases sharply as we increase the threads up to 8, at which point the algorithm reaches its optimal performance. The intriguing aspect is that for the smaller 10k-node graph, the execution time continues to decrease (or at least flatten out) up to 24 threads, while for the larger 1M and 10M-node graphs, the execution time increases after 8 threads. This is because the massive workload of the larger graphs pushes the system to its limits, and using more than 8 threads (likely the number of high-performance cores) introduces significant overhead from resource contention. When more threads than the optimal number are used, the overhead from context switching and competition for shared resources begins to outweigh the parallelization gains, causing the total duration to increase. This behavior is not seen on the smaller 10k V1 graph because its workload is not large enough to trigger this level of contention.
\includegraphics[width=0.52\textwidth, height=10cm, keepaspectratio]{charts/Parallel Edge V2 - Graph 10ml Nodes - Intel Core i7 14th gen.png}

This analysis highlights that for effective parallelization, the choice of algorithm and data structure is as important as the number of threads. An efficient underlying algorithm is a prerequisite for achieving meaningful speedup from parallel execution.

\subsection{Parallel Edge Iterator V3: final version}
This final version of the Edge Algorithm is similar to the V3 version of the Node/Forward algorithm, whith whom it shares significant enhancements. Instead of a standard \texttt{std::map}, \texttt{std::unordered\_map} is used for the adjacency list and ranks. This provides an average-case time complexity of $\mathcal{O}(1)$ for accessing a node's neighbors, which is significantly faster than the $\mathcal{O}(\log N)$ of std::map, especially for large graphs. The parallelization is implemented using the \texttt{std::async} and \texttt{std::future} library, so by means of OS managed tasks. Within each thread, the \texttt{threadFunction} function contains its own set of optimizations: we use again \textbf{Two-Pointer Intersection} to find common neighbors by resorting to two iterators and advancing them based on which neighbor is smaller. It's important to first sort the neighbors lists of nodes $v0$ and $v1$, which is done at the beginning of the program. Overall, this approach is much faster than an $\mathcal{O}(\text{deg}_{v0} \times \text{deg}_{v1})$ naive nested loop approach or a hash-set based approach which would have hashing overhead. Also, we get rid of \textbf{redundant ranks check} by already pre-filtering the edges so that we only have edges \texttt{(u,v)} where \texttt{rank(u)<rank(v)}. This means the main loop in thread function does not need to check if (ranks.at(v0) < ranks.at(v1)). By doing this, we \textit{de facto} work with \textbf{directed edges}. Moreover, the neighbor lists (\texttt{v0\_neighbors}, \texttt{v1\_neighbors}) and the ranks map are passed by \texttt{const \&} (\textbf{constant reference}), to avoid expensive copying operations. Last but not least, each thread maintains a \textbf{local variable to count triangles}. This completely eliminates the need for thread synchronization primitives like mutexes or atomic operations, as there is no shared state being modified concurrently. The results are aggregated at the end, which is a very clean and efficient parallel pattern.

\section{CUDA Parallel Edge Iterator Algorithms}
The Edge Iterator method presents a powerful approach to triangle counting on GPUs by assigning a dedicated thread to each edge, (u,v), in the graph. This strategy effectively distributes the computational workload across the thousands of processing cores available on a GPU. To facilitate efficient data handling and access, the graph's sparse adjacency list is converted to the \textbf{Compressed Row Storage (CRS)} format on the host, which is then transferred to the GPU's global memory. The core of the algorithm is implemented within a CUDA \texttt{kernel function}, where each thread independently processes its assigned edge to identify potential common neighbors. To ensure the integrity of the total triangle count, which is updated concurrently by multiple threads, the \texttt{atomicAdd} function is employed, effectively preventing race conditions without the performance overhead of mutexes.

Our implementations are structured around two distinct base algorithmic approaches, which are then combined with two key optimization strategies to create a family of increasingly efficient versions. The fundamental difference between our primary algorithmic approaches lies in how each thread finds the common neighbors for its assigned edge (u,v). \textbf{Version 1 (v1)} employs a naive nested-loop intersection, while \textbf{Version 2 (v2)} utilizes a more efficient two-pointer merge-like algorithm. On top of these, we apply two optimization strategies: using chunked kernel launches and shared memory, applied both separately and in combination.

\subsection{v1 Implementations}

\begin{enumerate}
\item \textbf{CUDA Parallel Edge v1:} This is our baseline implementation and the most straightforward version. For a given edge, each thread finds common neighbors by performing a \textbf{naive nested-loop intersection} on the adjacency lists of the two connected vertices. The time complexity of this step is O(d(u)${\cdot}$d(v)), which, while simple, can be a significant performance bottleneck for edges connected to high-degree nodes. This version launches a single kernel to process all edges in a single, large batch.
\item \textbf{CUDA Parallel Edge v1\_1:} This version builds on the v1 algorithm by introducing a \textbf{chunked parallelization} strategy. Instead of launching a single kernel to process all edges, the algorithm partitions the edges into smaller chunks and launches a series of kernels, one for each chunk. The goal is to investigate whether this approach can improve GPU resource utilization and latency hiding by allowing the scheduler to manage smaller, more frequent parallel tasks more effectively. The underlying intersection logic within the kernel remains the same naive nested-loop approach as v1.
\item \textbf{CUDA Parallel Edge v1\_2:} This is our most advanced implementation of the v1 family. It combines the naive nested-loop intersection of v1 with both the \textbf{chunked parallelization} and \textbf{shared memory} strategies. For each edge, the thread first copies the adjacency lists from global memory to the faster shared memory. It then performs the naive nested-loop intersection directly from shared memory, drastically reducing memory access latency and leading to a significant performance improvement over versions that rely solely on global memory.
\end{enumerate}
